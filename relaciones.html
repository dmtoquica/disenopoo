Relaciones entre clases y herencia

Una explicación visual de cómo se conectan las clases y cómo esas relaciones se representan en UML, antes de pasar a la herencia con Java.

1. ¿Cómo se relacionan dos clases?

No todas las relaciones significan lo mismo. La diferencia está en el tipo de vínculo y en el grado de dependencia entre las clases.

01 · Asociación

Una clase se relaciona con otra

Las dos pueden existir independientemente.

02 · Dependencia

Una clase usa a otra

El uso normalmente es temporal, por ejemplo mediante un parámetro.

03 · Agregación

Un todo agrupa partes

Las partes pueden continuar existiendo sin el todo.

04 · Composición

Un todo está formado por partes

Las partes dependen de la existencia del todo.

2. Las relaciones en UML

Aquí aparece la diferencia que suele confundirse: cada relación tiene una representación gráfica distinta.

Asociación: línea continua

Forma: línea continua.
Significado: las clases se conocen o se relacionan.
Existencia: ambas pueden existir independientemente.
Ejemplo: Profesor — Curso. Un profesor puede existir aunque en ese momento no tenga un curso asignado; un curso también puede existir sin profesor asignado.

Dependencia: línea discontinua con flecha abierta

Forma: línea discontinua.
Flecha: abierta y apunta hacia la clase de la que se depende.
Uso: una clase necesita a otra para realizar una operación.
Ejemplo: imprimir(Documento doc). La impresora usa el documento durante la operación; no necesariamente lo guarda como atributo.

Agregación: línea continua + rombo vacío

Forma: línea continua + rombo vacío.
Rombo: se coloca junto al “todo”, aquí Equipo.
Existencia: el Jugador puede vivir fuera del Equipo.
Ejemplo: Equipo — Jugador. Si el equipo desaparece, los jugadores siguen existiendo y pueden pasar a otro equipo.

Composición: línea continua + rombo lleno

Forma: línea continua + rombo lleno.
Rombo: se coloca junto al “todo”, aquí Casa.
Existencia: la parte depende conceptualmente del todo.
Ejemplo del material: Casa — Habitaciones. Las habitaciones se entienden como partes de la Casa y dependen de esa composición.

4. Herencia: otra clase de relación

Aquí ya no hablamos de “tiene un”, sino de “es un”.

Generalización: Carro + Moto → Vehículo. Buscamos lo que comparten.
Especialización: Vehículo → Carro / Moto. Agregamos lo específico.

5. La misma idea en Java

class Gerente extends Empleado { }

extends indica que Gerente hereda de Empleado.

public Gerente(String nombre, double salario, double bono) { super(nombre, salario); this.bono = bono; }

super(...) llama al constructor de la superclase.

class Empleado { protected String nombre; protected double salarioBase; }

En esta jerarquía, protected permite que las subclases accedan directamente a esos miembros.

class Empleado { protected String nombre; protected double salarioBase; public Empleado(String nombre, double salarioBase) { this.nombre = nombre; this.salarioBase = salarioBase; } public double calcularSalario() { return salarioBase; } } class Gerente extends Empleado { private double bono; Gerente(String nombre, double salario, double bono) { super(nombre, salario); this.bono = bono; } double calcularSalarioTotal() { return calcularSalario() + bono; } } class Operario extends Empleado { private int horasExtra; Operario(String nombre, double salario, int horasExtra) { super(nombre, salario); this.horasExtra = horasExtra; } double calcularSalarioTotal() { return calcularSalario() + horasExtra * 15000; } }

6. Principio de Sustitución de Liskov

La pregunta central es si una subclase puede ocupar el lugar de la superclase sin romper lo que el programa espera.

Problema: si un código espera poder cambiar ancho y alto de forma independiente, un Cuadrado que obliga a mantenerlos iguales puede romper esa expectativa.

Aplicado a Empleado

Gerente: conserva el comportamiento esperado de Empleado y agrega bono.
Operario: conserva el comportamiento esperado y agrega horas extra.
Practicante: conserva el comportamiento heredado y agrega su particularidad.
