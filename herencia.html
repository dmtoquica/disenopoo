Herencia, LSP y Polimorfismo

Vamos a pasar de tener clases relacionadas a construir jerarquías de clases donde una clase puede reutilizar, especializar y redefinir el comportamiento de otra.

¿Dónde estamos?

Ya conocemos diferentes formas de relacionar clases. Ahora vamos a estudiar una relación especialmente importante: la herencia.

ANTES

Relaciones entre clases

Las clases podían relacionarse mediante asociación, dependencia, agregación y composición.

AHORA

Herencia

Una clase puede tomar como base otra clase y especializar su comportamiento.

DESPUÉS

Polimorfismo

Una misma operación puede producir comportamientos diferentes dependiendo del objeto que la ejecute.

Idea central:
La herencia no significa simplemente "copiar código". Representa una relación conceptual donde una clase especializada puede ser tratada como una instancia de una clase más general.

1. ¿Qué es la herencia?

La herencia permite crear una nueva clase a partir de otra existente.

Piensa en una clasificación

Supongamos que tenemos diferentes tipos de empleados:

Empleado
- nombre
- salario

+ trabajar()
↓
Gerente
- departamento

+ trabajar()
+ dirigir()
Operario
- turno

+ trabajar()
+ operarMaquina()

Empleado es la clase general. Gerente y Operario son especializaciones.

Generalización

Partimos de clases específicas para identificar características comunes y llevarlas a una clase más general.

Ejemplo: Gerente y Operario tienen nombre, identificación, salario y comportamiento laboral. Esas características pueden pertenecer a Empleado.

Especialización

Partimos de una clase general y creamos clases más específicas.

Ejemplo: Un Gerente es un Empleado, pero además tiene responsabilidades propias de su rol.

2. La palabra clave extends

En Java, extends indica que una clase hereda de otra.

class Empleado { String nombre; double salario; void trabajar() { System.out.println("El empleado está trabajando"); } } class Gerente extends Empleado { String departamento; void dirigir() { System.out.println("El gerente está dirigiendo"); } }
¿Qué significa?
Gerente hereda de Empleado. Por lo tanto, un objeto Gerente puede utilizar los miembros heredados que sean accesibles.

La relación se puede leer así:

Gerente ES UN Empleado.

Esta frase es muy importante cuando estamos diseñando una jerarquía. Si no podemos expresar razonablemente la relación como "X es un Y", probablemente no estamos frente a una buena relación de herencia.

Probemos mentalmente

¿Un Gerente puede ser tratado como un Empleado?

3. La palabra clave super

super permite acceder a elementos de la superclase.

Llamar al constructor de la superclase

class Empleado { protected String nombre; Empleado(String nombre) { this.nombre = nombre; } } class Gerente extends Empleado { String departamento; Gerente(String nombre, String departamento) { super(nombre); this.departamento = departamento; } }

super(nombre) llama al constructor de Empleado.

Llamar a un método de la superclase

class Empleado { void trabajar() { System.out.println("Trabajo general"); } } class Gerente extends Empleado { @Override void trabajar() { super.trabajar(); System.out.println("Además, coordino el equipo"); } }

Aquí super.trabajar() permite conservar el comportamiento de la superclase y agregar comportamiento específico.

4. El modificador protected

Una herramienta importante cuando trabajamos con herencia.

Modificador Idea principal
private Acceso restringido a la propia clase.
protected Accesible desde la clase y desde sus subclases, además de las reglas de acceso de paquete.
public Accesible desde cualquier lugar donde sea visible la clase.

Ejemplo

class Empleado { protected double salario; } class Gerente extends Empleado { void mostrarSalario() { System.out.println(salario); } }
Pero cuidado: protected no significa "todo vale". La visibilidad sigue siendo parte del diseño de la clase.

5. Herencia en UML

En UML la herencia se representa mediante una línea con un triángulo vacío que apunta hacia la superclase.

Empleado
- nombre : String
- salario : double

+ trabajar() : void
△
Gerente
- departamento : String

+ dirigir() : void
Operario
- turno : String

+ operarMaquina() : void
Recuerda la dirección:
El triángulo apunta hacia la clase más general.

¿Por qué usar herencia?

Reutilización

Permite aprovechar características comunes.

Organización

Permite construir jerarquías conceptuales.

Especialización

Las subclases pueden agregar comportamiento propio.

Polimorfismo

Permite trabajar con objetos especializados desde referencias generales.

6. Taller: Jerarquía de empleados

Construyamos una jerarquía sencilla en Java.

La situación

Una empresa tiene diferentes tipos de empleados. Todos comparten información básica, pero cada tipo puede tener comportamientos particulares.

Empleado
# nombre : String
# salarioBase : double

+ trabajar() : void
↓
Gerente
- bono : double

+ dirigir() : void
Operario
- horasExtra : int

+ operar() : void

Una posible implementación

class Empleado { protected String nombre; protected double salarioBase; Empleado(String nombre, double salarioBase) { this.nombre = nombre; this.salarioBase = salarioBase; } void trabajar() { System.out.println(nombre + " está trabajando"); } }
class Gerente extends Empleado { private double bono; Gerente( String nombre, double salarioBase, double bono ) { super(nombre, salarioBase); this.bono = bono; } void dirigir() { System.out.println("El gerente dirige el equipo"); } }
class Operario extends Empleado { private int horasExtra; Operario( String nombre, double salarioBase, int horasExtra ) { super(nombre, salarioBase); this.horasExtra = horasExtra; } void operar() { System.out.println("El operario trabaja en producción"); } }

Ahora pensemos como diseñadores

  • ¿Qué atributos realmente pertenecen a todos los empleados?
  • ¿Qué comportamientos son comunes?
  • ¿Qué comportamientos son específicos?
  • ¿Qué información debería estar protegida?
  • ¿Qué comportamiento podría cambiar en cada subclase?

7. Principio de Sustitución de Liskov

LSP: una subclase debe poder utilizarse allí donde se espera su superclase sin romper las expectativas del programa.

La pregunta clave

Si tengo un objeto de la subclase, ¿puedo utilizarlo como si fuera un objeto de la superclase sin que el programa deje de comportarse correctamente?

Un ejemplo clásico: vehículos

class Ave { void volar() { System.out.println("Estoy volando"); } } class Aguila extends Ave { @Override void volar() { System.out.println("El águila vuela"); } } class Pinguino extends Ave { @Override void volar() { // ¿Qué hacemos aquí? throw new UnsupportedOperationException(); } }
Problema: si Ave promete que sus objetos pueden volar, Pinguino no cumple esa expectativa. La jerarquía está expresando una relación incorrecta.

¿Dónde está el problema?

Una posible corrección

En lugar de obligar a todas las aves a volar, podemos diseñar una abstracción más adecuada.

class Ave { // características comunes } interface Volador { void volar(); } class Aguila extends Ave implements Volador { public void volar() { System.out.println("El águila vuela"); } } class Pinguino extends Ave { // No está obligado a implementar volar() }
Idea: no debemos forzar a una subclase a cumplir comportamientos que contradicen lo que realmente representa.

8. Primer acercamiento al polimorfismo

La misma operación puede comportarse de manera diferente según el objeto.

Sobreescritura de métodos

class Empleado { void trabajar() { System.out.println("Trabajo de empleado"); } } class Gerente extends Empleado { @Override void trabajar() { System.out.println("El gerente coordina"); } } class Operario extends Empleado { @Override void trabajar() { System.out.println("El operario produce"); } }

¿Qué sucede aquí?

Empleado e1 = new Gerente(); Empleado e2 = new Operario(); e1.trabajar(); e2.trabajar();
e1.trabajar()
Ejecuta la versión de Gerente.
e2.trabajar()
Ejecuta la versión de Operario.

¿Y si calculamos el salario?

class Empleado { double calcularSalario() { return 1500000; } } class Gerente extends Empleado { @Override double calcularSalario() { return 3500000; } } class Operario extends Empleado { @Override double calcularSalario() { return 2200000; } }

La operación se llama igual, pero cada objeto proporciona su propia implementación.

9. Clases y métodos abstractos

Una clase abstracta permite definir una base común sin necesariamente proporcionar una implementación completa para todos sus comportamientos.

abstract class Empleado { protected String nombre; Empleado(String nombre) { this.nombre = nombre; } abstract double calcularSalario(); void mostrarNombre() { System.out.println(nombre); } }
Importante:
No podemos hacer directamente:

Empleado e = new Empleado("Ana");

porque Empleado es abstracta.

Las subclases completan el comportamiento

class Gerente extends Empleado { Gerente(String nombre) { super(nombre); } @Override double calcularSalario() { return 3500000; } }

10. Reto de diseño

Ahora analiza antes de escribir código.

Una empresa tiene:
  • Empleados.
  • Gerentes.
  • Operarios.
  • Todos tienen nombre e identificación.
  • Todos deben poder calcular su salario.
  • El salario de un gerente incluye un bono.
  • El salario de un operario depende de sus horas trabajadas.

Preguntas para diseñar la solución

1. ¿Cuál debería ser la superclase?

Empleado. Es la abstracción general que contiene las características comunes.
2. ¿Cuáles serían las subclases?

Gerente y Operario. Son especializaciones de Empleado.
3. ¿Dónde debería estar calcularSalario()?

En la clase abstracta Empleado como método abstracto, para que cada subclase implemente su propia forma de calcularlo.

Solución conceptual

<<abstract>> Empleado
# nombre : String
# identificacion : String

+ calcularSalario() : double
△
Gerente
- bono : double

+ calcularSalario() : double
Operario
- horas : int

+ calcularSalario() : double

Implementación final

abstract class Empleado { protected String nombre; protected String identificacion; Empleado(String nombre, String identificacion) { this.nombre = nombre; this.identificacion = identificacion; } abstract double calcularSalario(); } class Gerente extends Empleado { private double bono; Gerente( String nombre, String identificacion, double bono ) { super(nombre, identificacion); this.bono = bono; } @Override double calcularSalario() { return 3500000 + bono; } } class Operario extends Empleado { private int horas; Operario( String nombre, String identificacion, int horas ) { super(nombre, identificacion); this.horas = horas; } @Override double calcularSalario() { return horas * 12000; } }
